# Backlog

- **Concours & Prix mensuels** : Promouvoir certains exploits avec des concours sponsorisés par des entreprises (idée mentionnée par l'utilisateur : "prix et concours mensuel etc.").
- **Génération IA plus fine** : Ajuster les prompts pour mieux contextualiser les défis à l'Afrique francophone (matériaux, environnements spécifiques).
- **Application mobile dédiée** : Transformer cette PWA (TanStack Start) en application mobile native ou Capacitor pour simplifier la prise de photo.
- **Paramétrage des récompenses** : Permettre au parent de configurer des cadeaux physiques ou monétaires débloqués en fonction des points de talents accumulés.
- **Confirmation du guide de marque officiel** : Si l'utilisateur obtient un fichier de police source ou un guide de marque pour le logo, revérifier le choix "Fredoka" comme police d'affichage (cf. [[genizio-decisions]] #6 — actuellement une estimation visuelle, pas une valeur confirmée).
- **Refonte UI globale** : L'utilisateur juge l'UI actuelle "AI-generated" / générique au-delà de la seule question de la police — discussion explicitement mise en pause le temps de traiter Naya en premier ("avant de parler de l'ui globale je vais parler de l'IA interne"). Reprendre cette conversation une fois Naya scoping terminé. Une tentative d'import via un wireframe Claude Design (`Génizio Wireframes.dc.html`) a échoué faute d'accès (voir [[genizio-etat-code]]) — reste à trouver un moyen d'en récupérer le contenu (export/partage claudeusercontent.com, ou fichier local).
- **Audit ligne à ligne post-rename** : `genizio_etat_code.md` "Ce qui est en place et fonctionne" date du 2026-07-15 et n'a pas été re-vérifié fonctionnellement depuis (seuls les textes/branding ont changé). Faire un passage de vérification directe dans le navigateur des flux clés (génération de défi, validation de preuve) avant la prochaine session de fonctionnalités.
- **Vue Postgres dédiée pour le Mur public** : la policy RLS publique sur `child_profiles` (cf. [[genizio-decisions]] #10) expose encore toutes les colonnes (âge, ville, pays, talents...) des profils ayant un défi complété, alors que `/feed` n'a besoin que de `name` et `avatar_color`. Créer une vue/RPC dédiée n'exposant que ces deux colonnes, puis migrer `feed.tsx` dessus.
- **Audit RLS complet du schéma** : seules `child_profiles` et `challenges` ont été vérifiées via `pg_policies` le 2026-07-16. Les autres tables (bucket `proofs`, etc.) n'ont pas été auditées avec la même rigueur — à faire avant toute mise en production réelle avec de vrais utilisateurs.
- **Rotation de `ANTHROPIC_API_KEY`** : cette clé a été commitée dans `.env` et poussée sur GitHub (repo privé `mercurebeauty-eng/geniusio`, commit `31d48ea`) avant d'être retirée du suivi git le 2026-07-16 (cf. [[genizio-decisions]]). Le repo étant privé le risque est contenu, mais la clé reste dans l'historique git — recommandé de la régénérer sur console.anthropic.com par précaution.
- **Les Guildes Génizio** : 6 familles de talents (Bâtisseurs, Inventeurs, Explorateurs, Créateurs, Stratèges, Protecteurs du Vivant) pour organiser la communauté — projets collaboratifs, défis collectifs, mentorat entre pairs. Vision détaillée dans [[genizio-vision]] § Extension écosystème. Aucune table `guilds` en base, aucun écran. Nécessite de clarifier la relation avec la taxonomie des 9 clés Gardner déjà utilisée par la Carte des Talents avant de commencer (les deux vocabulaires ne se recouvrent pas 1:1).
- **Génizio Admin OS** : dashboard interne complet (KPIs, cartographie géographique, module Talents/Défis/IA/Communauté/Événements/Écoles/Fondation/Commerce). Spec détaillée dans [[genizio-vision]]. Gros morceau séparé de l'app actuelle — nécessiterait son propre rôle "Administrateur" (absent du schéma) et probablement une app/route distincte protégée. Rien commencé.
- **Boutique de kits — Phases 0 à 3 terminées** (cf. [[genizio-decisions]] #12, #14, #17, #18, #19) : catalogue produits + file `material_suggestions` + badges "Kit disponible" sur dashboard/cartes fermées/ouvertes + bloc de commande actionnable sur le dashboard + page `/boutique` dédiée (kit comme point d'entrée : bouton "Générer un défi" à partir d'un kit) + table `orders` avec suivi admin + `WhatsAppFAB` global. Reste :
  - **Phase 4 (volontairement pas scopée)** : vrai paiement Mobile Money in-app, une fois la demande validée via les commandes déjà trackées dans `orders`.
- **`WhatsAppFAB` sans contexte enfant réel** : le composant (`src/components/WhatsAppFAB.tsx`) accepte une prop `childContext` (nom/âge/guilde/nb de défis) pour personnaliser le message pré-rempli, mais `__root.tsx` le monte globalement sans jamais la passer (`<WhatsAppFAB />` sans props) — le message est donc toujours le générique "j'ai besoin d'aide", jamais contextualisé. Pour l'activer, il faudrait le sortir du root et le remonter par route enfant-scopée (`/profiles/$profileId/*`) avec le profil courant, ou passer le contexte via un contexte React/route loader partagé.
- **Audit ownership des routes `/profiles/$profileId/*`** : ces routes (challenges, portfolio, quest, mentors) lisent `child_profiles`/`challenges` via `.eq("id", profileId)` sans vérifier `user_id`, en comptant sur RLS. Depuis que la policy publique (défi complété → lisible par tous, cf. [[genizio-decisions]] #10) existe, naviguer directement vers l'URL d'un enfant public d'une autre famille (UUID exact requis) donnerait accès à sa page de gestion complète — pas juste au Mur Public. Risque réduit après le fix de [[genizio-decisions]] #13 (les listes/sélecteurs ne fuitent plus l'UUID), mais reste une dette d'architecture : ajouter un contrôle d'ownership explicite (`.eq("user_id", session.user.id)`) sur ces 4 routes plutôt que de compter implicitement sur RLS.
- **Camps / Labs / Centers Génizio** : le reste du modèle de revenus long terme (camps d'immersion, espaces physiques, accompagnement avancé) — l'utilisateur identifie les Camps comme "l'une des premières sources de revenus". Pas commencé, distinct de la boutique de kits ci-dessus. Cf. [[genizio-vision]].
- **Nouveaux rôles de plateforme** : Superviseur, Mentor (expert volontaire — distinct du "mentor" déjà implémenté via `child_mentors`/lien de partage, qui est plus proche d'un accès en lecture qu'un rôle actif), École, Administrateur, Fondation. Le schéma actuel ne connaît que parent + enfant + (depuis peu) mentor en lecture seule. À anticiper avant de complexifier le modèle de données si ces rôles se confirment.
