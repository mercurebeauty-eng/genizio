# Backlog

- **Concours & Prix mensuels** : Promouvoir certains exploits avec des concours sponsorisés par des entreprises (idée mentionnée par l'utilisateur : "prix et concours mensuel etc.").
- **Génération IA plus fine** : Ajuster les prompts pour mieux contextualiser les défis à l'Afrique francophone (matériaux, environnements spécifiques).
- **Application mobile dédiée** : Transformer cette PWA (TanStack Start) en application mobile native ou Capacitor pour simplifier la prise de photo.
- **Paramétrage des récompenses** : Permettre au parent de configurer des cadeaux physiques ou monétaires débloqués en fonction des points de talents accumulés.
- **Confirmation du guide de marque officiel** : Si l'utilisateur obtient un fichier de police source ou un guide de marque pour le logo, revérifier le choix "Fredoka" comme police d'affichage (cf. [[genizio-decisions]] #6 — actuellement une estimation visuelle, pas une valeur confirmée).
- **Refonte UI globale** : L'utilisateur juge l'UI actuelle "AI-generated" / générique au-delà de la seule question de la police — discussion explicitement mise en pause le temps de traiter Naya en premier ("avant de parler de l'ui globale je vais parler de l'IA interne"). **Mise à jour 2026-07-20 : le scoping Naya est fait** ([[genizio-naya-systeme-comprehension]], décision #27) — la conversation refonte UI peut être reprise quand l'utilisateur le souhaite. Une tentative d'import via un wireframe Claude Design (`Génizio Wireframes.dc.html`) a échoué faute d'accès (voir [[genizio-etat-code]]) — reste à trouver un moyen d'en récupérer le contenu (export/partage claudeusercontent.com, ou fichier local).
- **Audit ligne à ligne post-rename** : `genizio_etat_code.md` "Ce qui est en place et fonctionne" date du 2026-07-15 et n'a pas été re-vérifié fonctionnellement depuis (seuls les textes/branding ont changé). Faire un passage de vérification directe dans le navigateur des flux clés (génération de défi, validation de preuve) avant la prochaine session de fonctionnalités.
- **Vue Postgres dédiée pour le Mur public** : la policy RLS publique sur `child_profiles` (cf. [[genizio-decisions]] #10) expose encore toutes les colonnes (âge, ville, pays, talents...) des profils ayant un défi complété, alors que `/feed` n'a besoin que de `name` et `avatar_color`. Créer une vue/RPC dédiée n'exposant que ces deux colonnes, puis migrer `feed.tsx` dessus.
- **Audit RLS complet du schéma — fait le 2026-07-17** (cf. [[genizio-decisions]] #22) : toutes les tables + buckets storage passés en revue, 4 failles réelles trouvées et corrigées (posts, proofs, orders, generateChallenges). `get_advisors` propre hormis 3 items déjà connus/acceptés (material_suggestions sans policy par design, listing public des buckets, protection mot de passe désactivée — non pertinent en Google-only). Reste : re-auditer si de nouvelles tables/buckets sont ajoutés, ce n'est pas un audit "une fois pour toutes".
- **Rotation de `ANTHROPIC_API_KEY`** : cette clé a été commitée dans `.env` et poussée sur GitHub (repo privé `mercurebeauty-eng/geniusio`, commit `31d48ea`) avant d'être retirée du suivi git le 2026-07-16 (cf. [[genizio-decisions]]). Le repo étant privé le risque est contenu, mais la clé reste dans l'historique git — recommandé de la régénérer sur console.anthropic.com par précaution.
- **Les Guildes Génizio** : 6 familles de talents (Bâtisseurs, Inventeurs, Explorateurs, Créateurs, Stratèges, Protecteurs du Vivant) pour organiser la communauté — projets collaboratifs, défis collectifs, mentorat entre pairs. Vision détaillée dans [[genizio-vision]] § Extension écosystème. Aucune table `guilds` en base, aucun écran. Nécessite de clarifier la relation avec la taxonomie des 9 clés Gardner déjà utilisée par la Carte des Talents avant de commencer (les deux vocabulaires ne se recouvrent pas 1:1).
- **Génizio Admin OS** : dashboard interne complet (KPIs, cartographie géographique, module Talents/Défis/IA/Communauté/Événements/Écoles/Fondation/Commerce). Spec détaillée dans [[genizio-vision]]. Gros morceau séparé de l'app actuelle — nécessiterait son propre rôle "Administrateur" (absent du schéma) et probablement une app/route distincte protégée. Rien commencé.
- **Boutique de kits — Phases 0 à 3 terminées** (cf. [[genizio-decisions]] #12, #14, #17, #18, #19) : catalogue produits + file `material_suggestions` + badges "Kit disponible" sur dashboard/cartes fermées/ouvertes + bloc de commande actionnable sur le dashboard + page `/boutique` dédiée (kit comme point d'entrée : bouton "Générer un défi" à partir d'un kit) + table `orders` avec suivi admin + `WhatsAppFAB` global. Reste :
  - **Phase 4 (volontairement pas scopée)** : vrai paiement Mobile Money in-app, une fois la demande validée via les commandes déjà trackées dans `orders`.
- **Camps / Labs / Centers Génizio** : le reste du modèle de revenus long terme (camps d'immersion, espaces physiques, accompagnement avancé) — l'utilisateur identifie les Camps comme "l'une des premières sources de revenus". Pas commencé, distinct de la boutique de kits ci-dessus. Cf. [[genizio-vision]].
- **Nouveaux rôles de plateforme** : Superviseur, Mentor (expert volontaire — distinct du "mentor" déjà implémenté via `child_mentors`/lien de partage, qui est plus proche d'un accès en lecture qu'un rôle actif), École, Administrateur, Fondation. Le schéma actuel ne connaît que parent + enfant + (depuis peu) mentor en lecture seule. À anticiper avant de complexifier le modèle de données si ces rôles se confirment.
- **Mur Public — likes/commentaires réels, fait le 2026-07-17** (cf. [[genizio-decisions]] #22) : tables `post_likes`/`comments` + trigger `SECURITY DEFINER` pour synchroniser `posts.likes_count`. Le bouton commentaire n'affiche pas de nom de famille (juste "Vous"/"Un parent"), cohérent avec la politique de confidentialité — à revisiter si un jour un vrai profil public/pseudo est introduit. Le bouton "Partager" copie juste le lien de la photo dans le presse-papiers (pas de route `/feed/:postId` dédiée) — pourrait être amélioré avec une vraie page de post individuel si le partage devient un usage réel.
- **🟡 Superviseur Copilote (2026-08-15, décision #74 — PRODUIT VERROUILLÉ, NON implémenté)** : pour les enfants **accompagnés** (pack `accompaniment_pack` ou compartiment séances de campagne), le superviseur devient l'opérateur principal du cycle de vie des défis ; le parent passe en validateur (veto + bilan). Feuille de route d'implémentation, par ordre de dépendance :
  1. **`supervisor_actions` (journal d'audit)** — table (supervisor_user_id, child_id, challenge_id, action, created_at) + écriture sur chaque mutation superviseur. Pré-requis de tout le reste (un tiers qui écrit → on trace).
  2. **Couche d'autorisation `canOperate(childId, userId)`** — pure testée : parent **ou** (superviseur actif assigné **et** enfant accompagné via `family_coverages` source `accompaniment_pack`/campagne). Brancher les mutations de défis (start/progress/notes/abandon/génération/assignation) sur ce choke-point au lieu du `.eq("user_id", context.userId)` naïf ; `challenges.user_id` **reste le parent**, ajouter `created_by_user_id` pour l'attribution.
  3. **UI superviseur** (extension de `supervisor.tsx`) — les cartes des enfants accompagnés passent en mode opérateur : démarrer/progresser, notes de séance, abandon (motif), générer/assigner, soumettre la preuve (photo en séance → `validateChallengeProof` autorisé via `canOperate`, ou champ déclaratif décision #36). Jamais de suppression, jamais de publication.
  4. **`supervisor_reports` (bilan de fin, le « bilan inclus »)** — table (child_id, supervisor_user_id, period, sections : réalisations / compétences observées / recommandations, status draft|submitted|validated, validated_by/at) + rédaction depuis `/supervisor` + carte « Bilan du superviseur » dans le portfolio + validation parent explicite + export PDF/WhatsApp.
  5. **Payout — bilan = condition de paiement** — la dernière séance d'une période n'est payable (`approveSupervisorSessionAdmin`) que si le bilan est rendu et validé ; à définir précisément (fenêtre, bordereaux).
  6. **UX parent** — bandeau « Mode accompagnement — suivi par [prénom] » + boutons Réouvrir (un clic, à tout moment) / Voir le bilan. Le parent reste opérateur par défaut sur ses enfants non accompagnés.
  7. **Score V2** — inchangé (mesure l'opérateur) ; recalibrage différé si le volume de feedback le justifie.
  - **Contraintes connues** : la chaîne IA de validation (`validateChallengeProof`, points/Jumeau/observations) n'est **pas modifiée** — seul l'acteur qui soumet change ; RLS des tables superviseur reste service-role (pas de policy directe) ; migrations à pousser via CLI local (jamais MCP Supabase, cf. MEMORY principe 8).
